# robot_docking_manager

`robot_docking_manager` is the sensor-independent near-field docking controller for the Ranger Mini 3 charging dock. Long-range return-to-dock remains a Nav2 task. The product default is the calibrated Orbbec 336L typed observation; the front GS2 scan is retained only as an explicit rollback backend.

Runtime contract:

- Lifecycle: resident common service started by `run_common_services.sh`; idle until `/docking/start` or `/docking/undock`
- Observation backend: `gs2_scan` from `/dock/gs2_scan`, or `target_observation` from `/dock/target_observation`
- Charging state: `/battery_state`
- Undock odometry confirmation: `/local_state/odometry`
- Start/stop/undock services: `/docking/start`, `/docking/stop`, `/docking/undock`
- Status: `/docking/status`
- Command output: `/cmd_vel_docking`
- Mode request: `/ranger_mini3/forced_mode=spinning` while yaw is outside fine-docking tolerance, `/ranger_mini3/forced_mode=side_slip` for lateral/forward fine docking, then `auto` on stop or `park` after charging is detected
- Reverse enable: `/ranger_mini3/docking_allow_reverse=true` only during controlled undocking or a bounded contact-retry backoff, then `false`

The node deliberately publishes before `robot_safety`, not directly to `/cmd_vel_safe` or `/cmd_vel`. The command path remains:

```text
robot_docking_manager
  -> /cmd_vel_docking
  -> robot_safety
  -> /cmd_vel
  -> ranger_base_node
```

The generic `DockTargetObservation` contract uses `base_link`: positive lateral error means the dock center is toward vehicle +Y, and positive yaw error means the vehicle needs a counter-clockwise correction. Orbbec uses `controller.lateral_command_sign=+1`; the GS2 rollback profile retains `-1`. Camera mode disables blind acquisition, so an absent or invalid target produces zero speed rather than an open-loop approach. `NJRH_DOCKING_SENSOR_BACKEND` defaults to `orbbec_336l`; set `gs2` explicitly only for controlled rollback.

The Orbbec fixed-face observation hands off at `approach.final_target_distance_m=0.34`. Vision-guided approach is capped by `safety.max_linear_speed_mps=0.15`; after contact handoff the straight-only crawl starts at `controller.contact_crawl_speed_mps=0.05`. With `controller.contact_final_slow_zone_m=0.30`, the command drops to `controller.contact_final_crawl_speed_mps=0.02` after approximately the first `10 mm` of the bounded insertion, so the low-speed phase covers nearly the full contact approach and the measured approximately `35 mm` spring-contact compression. Its odometry bound remains `controller.contact_verify_max_distance_m=0.31`, and its time bound is `tolerances.contact_confirm_timeout_s=16.0`. `ContactVerify` is a one-way visual handoff: the calibrated protrusion is inside the camera blind zone after contact, so target observations can no longer change or abort insertion. Fresh odometry and BMS remain mandatory; `linear.y=0` and `angular.z=0` are fixed until contact, distance limit, or timeout.

Depth candidates are admitted only when their robust lateral span matches one of the calibrated feature profiles: the normal fixed-face profile (`0.235 +/- 0.060 m`) or the near protrusion profile (`0.113 +/- 0.025 m`, allowed only at a forward gap of `0.30 m` or less). This prevents an occluded slice of the approximately `0.77 m` background wall from becoming a high-confidence dock target after the protrusion disappears. The two-contact first-touch capture established the near protrusion's feature center at `y=-0.0418 m`; that offset is applied only to the near profile and is not used as a global camera/extrinsic correction.

If charging is still absent at the contact distance or time limit, camera mode does not retry in place. It enters the dedicated `ContactBackoff` state, publishes zero before changing direction, requests the normal straight-drive mode, enables controlled reverse, and backs out `0.60 m` at `0.06 m/s` using signed odometry progress. Backoff rejects stale odometry, more than `0.05 m` lateral drift, no first motion within `6 s`, no progress for `2 s`, or a total duration above `20 s`. Once clear, it disables reverse, restores `side_slip`, reacquires the camera target, and may attempt the straight insert again. `controller.contact_retry_max_count=2` bounds this sequence; exhausting the budget stops with a terminal failure rather than issuing unlimited blind pushes. This state is intentionally separate from `/docking/undock`, so retrying contact does not clear the persistent dock latch or trigger post-undock API behavior.

`/cmd_vel_docking` is published with `KEEP_LAST(1)` QoS. Docking velocity commands are latest-state control samples; stop and charging-contact zero commands must replace older nonzero docking commands instead of waiting behind a queue.

`rosbag` is not required for normal docking execution. It is still required for commercial tuning and regression: record the active observation (`/dock/gs2_scan` or `/dock/target_observation`), `/battery_state`, `/local_state/odometry`, `/tf`, `/cmd_vel_docking`, `/cmd_vel_collision_checked`, `/cmd_vel_safe`, `/ranger_mini3/forced_mode`, and `/ranger_base/status` during real docking trials.

The field profile is intentionally conservative: the active camera fixed-face yaw and lateral error are low-pass filtered and fine docking is staged by motion mode. On entering camera alignment, yaw must remain within the yaw exit tolerance of `0.5deg` for three consecutive observations. After that lock, the controller re-enters yaw correction at `1.0deg`; it stops forward/lateral motion, requests official Ranger `spinning` mode, and publishes a yaw-only command. Once yaw is settled it requests `side_slip` mode and publishes `angular.z=0` so `linear.y` alone corrects centerline error. This hysteresis removes a one-to-two-degree approach error without switching repeatedly on sub-degree camera noise. `controller.kyaw=0.70` provides the proportional correction, `controller.min_angular_speed_radps=0.05` keeps a requested correction above the chassis command deadband, and `safety.max_angular_speed_radps=0.12` bounds it. Docking remains serial: yaw, then lateral, then forward. `/docking/status` reports `phase`, `forced_mode`, `cmd_vx`, `cmd_vy`, `cmd_wz`, `yaw_realign_active`, `yaw_stable_frames`, and the detection geometry for field validation. At the calibrated first-contact handoff, `ContactVerify` explicitly fixes `linear.y=0` and `angular.z=0`; only the straight crawl remains (`0.05m/s`, capped at `0.02m/s` through the final `0.30m`), so the controller never rotates across energized metal contacts.

Charging detection is a global hard stop, but it is not a one-frame stop. The first accepted `/battery_state` charging indication enters `ContactStopping` and publishes zero velocity in the same callback. The 20 Hz control loop then keeps publishing zero through `/cmd_vel_docking -> robot_safety -> ranger_base`. Only feedback received after that BMS event is eligible for confirmation: `/motion_state` must remain fresh and `/wheel/odom.twist` must stay below `0.01 m/s` planar speed and `0.02 rad/s` yaw rate for at least `0.50 s` and five distinct wheel-odom samples. Only then does the controller disable reverse and request Park. `/motion_state` contains the official feedback mode but no velocity fields, so it is a freshness/mode witness; `/wheel/odom.twist` is the physical-speed witness. If either feedback stream is stale or the chassis is still moving after `3.0 s`, the controller logs a warning and continues publishing zero indefinitely instead of forcing Park. `/docking/status` and ROS logs expose `bms_to_first_zero_ms`, `first_zero_to_stop_ms`, `first_zero_to_stop_confirmed_ms`, `zero_cmd_count`, feedback ages, measured speeds, and motion mode. See `docs/docking_contact_stop.md` for the event contract.

Undocking is a separate low-speed safety strategy, not an App velocity command. `/docking/undock` is accepted from `Docked`, live charging contact, or the explicit persistent dock-contact latch written by BMS contact, docking success, or maintenance confirmation. Inference uses `power_supply_status=CHARGING/FULL`, charge current, `present=true` with valid voltage, or `present=true` with full SOC and valid voltage until a dedicated charging-contact GPIO/topic is available; full SOC plus pack voltage alone is not contact because the same values can appear away from the charger. The node releases park/charging hold, enables reverse at the Ranger mode controller, and backs out along `base_link` negative X using the retained calibrated speed `undock.speed_mps=0.06`. Completion is confirmed by actual planar movement on `undock.odom_topic`; elapsed command time is not treated as distance.

The charging dock is treated as a push-in spring mechanism: the robot charges only after pushing into the internal switch travel, so undocking must move continuously at the controlled speed through that same switch zone. The runtime must not replace this with a stop-and-wait de-energize gate, because stopping on the switch contact can leave the DC contacts arcing. Continuity is enforced downstream by `robot_safety`, which holds a fresh `/cmd_vel_docking` command inside its docking-priority window. Ordinary Nav2 reverse is bounded to MPPI terminal correction and does not own undocking.

The undock state machine separates release delay, first-motion wait, and after-motion progress monitoring. `undock.command_settle_s` lets park/forced-mode/reverse-enable changes settle before nonzero `/cmd_vel_docking` is sent. During the following `waiting_first_motion` phase the node must continuously publish `/ranger_mini3/docking_allow_reverse=true` and `/cmd_vel_docking.linear.x=-undock.speed_mps`; `undock.motion_start_timeout_s` is the grace window after that first nonzero command is sent, not a delay before sending commands. The retained calibrated speed remains `undock.speed_mps=0.06`.

`/docking/status` carries the state-machine evidence used for field diagnosis. Typical strings are `undocking command_settle elapsed=0.30/0.50 ...`, `undocking waiting_first_motion distance=0.000/0.600 cmd_x=-0.060 cmd_count=12 reverse_enable=true start_elapsed=0.6/6.0`, and `undocking active distance=0.034/0.600 cmd_x=-0.060 cmd_count=... last_progress_age=0.2`. If first odometry motion never exceeds `undock.progress_epsilon_m`, the failure is `undock_failed_motion_start_timeout distance=... cmd_count=... cmd_x=...`; `cmd_count=0` is classified separately as `undock_failed_no_command_published` because that is a state-machine command-publishing bug, not a chassis traction problem. Only after first motion does `undock.no_progress_timeout_s` detect a mid-undock stall and report `undock_failed_no_progress distance=...`. `undock.timeout_s` must cover command settle plus first-motion wait plus `undock.distance_m / undock.speed_mps` and margin. Commands still go through `/cmd_vel_docking` and `robot_safety`; any downstream obstacle, estop, or chassis rejection must stop the robot before `/cmd_vel`. This does not give Nav2 ownership of docking reverse; MPPI reverse is only a low-speed terminal correction.

For command-observation reconciliation, `/docking/status` now exposes parseable `phase`, `cmd_count`, `reverse_enable_count`, `last_cmd_x`, `last_cmd_stamp_age_s`, `command_start_elapsed_s`, `motion_start_timeout_s`, `first_motion_started`, and `failure_reason` fields on running and terminal undock states where applicable. A report with internal `cmd_count>0` but no observed `/cmd_vel_docking` sample is treated as an observer/topic-identity problem until the topic graph proves otherwise; `cmd_count=0` must not be reported as `undock_failed_motion_start_timeout`.
